# Приложение для онлайн-заказа еды (Food Delivery App) Тарабанов, Новгородов и Зайцев



---

## 1. Введение


**Food Delivery App** — это приложение для онлайн-заказа еды, которое объединяет пользователей, рестораны и службу доставки в единой системе.

Приложение позволяет:

- Просматривать каталог ресторанов и блюд.
- Искать блюда по названию и ингредиентам.
- Фильтровать предложения по цене, рейтингу, типу кухни и времени доставки.
- Добавлять товары в корзину и изменять их количество.
- Оформлять заказ с выбором способа оплаты и времени доставки.
- Отслеживать статус заказа.
- Просматривать историю заказов.
- Управлять личными данными и сохранёнными адресами. 

Основной сценарий работы пользователя выглядит следующим образом:

**Выбор ресторана → выбор товара → добавление в корзину → оформление заказа → оплата → приготовление → доставка → получение заказа.**

Проект реализуется как веб-приложение с отдельными клиентской и серверной частями. Клиентская часть отвечает за отображение интерфейса и взаимодействие с пользователем, серверная — за обработку данных, работу с заказами, пользователями, ресторанами и базой данных.

## 2. Основания для разработки


Разработка данного приложения инициирована на основе следующих факторов:

- **Анализ рынка:** высокий спрос на сервисы доставки готовой еды в городской среде (рост рынка на 25% в 2023–2024 гг.).
- **Бизнес-задача:** создание конкурентного решения, которое объединяет функцию агрегатора с собственной логистикой, снижая комиссию для ресторанов по сравнению с текущими крупными сервисами.
- **Техническая необходимость:** создание удобной системы, которая позволяет пользователям быстро находить блюда, оформлять заказы и получать информацию об их состоянии.
- **Интеграция:** возможность подключения внешних сервисов оплаты, уведомлений и других систем через API.
- **Внутренние потребности:** стандартизация процессов приёма заказов для ресторанов-партнёров и автоматизация работы курьерской службы.
- **Возможность развития:** приложение может расширяться за счёт подключения новых ресторанов, способов оплаты, программ лояльности и дополнительных функций.

## 3. Назначение продукта


### Целевая аудитория


1. **Конечные пользователи:** физические лица, желающие заказать еду с доставкой на дом или в офис.

2. **Рестораны и кафе:** заведения общественного питания, подключающиеся к платформе для размещения меню и приёма заказов.

3. **Администраторы платформы:** сотрудники, управляющие ресторанами, блюдами, акциями, пользователями и текущими заказами.

4. **Курьеры:** исполнители доставки, получающие информацию о заказах и адресах доставки.

Для каждой категории пользователей предусматриваются свои функции и права доступа.

### Основные бизнес-цели


- **Увеличение продаж:** обеспечение ресторанов дополнительным каналом сбыта.
- **Удобство пользователей:** интуитивно понятный интерфейс с минимальным количеством шагов для оформления заказа (от 3 до 5 кликов).
- **Автоматизация:** автоматизация процессов от принятия заказа до передачи информации на кухню ресторана.
- **Сокращение времени обработки:** уменьшение количества ручных операций при оформлении и обработке заказов.
- **Аналитика:** сбор данных о предпочтениях пользователей для построения персонализированных рекомендаций.
- **Развитие партнёрской сети:** возможность подключения новых ресторанов без значительной переработки системы.

## 4. Требования к ПО


Данный раздел описывает функциональные, нефункциональные и технологические требования, предъявляемые к разрабатываемой системе.

### 4.1. Функциональные требования


### Модуль аутентификации


- Регистрация пользователя по email и паролю.
- Авторизация зарегистрированного пользователя.
- Возможность входа через социальные сервисы Google и Apple.
- Восстановление пароля с подтверждением по SMS или Email.
- Выход из учётной записи.

### Каталог ресторанов и блюд


- Просмотр списка доступных ресторанов.
- Просмотр меню выбранного ресторана.
- Поиск по названию блюда и ингредиентам.
- Фильтрация по цене, рейтингу, типу кухни и времени доставки.
- Подгрузка изображений блюд через CDN.
- Отображение информации о доступности товара.

### Товар


Для каждого товара должна храниться и отображаться следующая информация:

- Название блюда.
- Описание блюда.
- Цена.
- Категория.
- Изображение.
- Информация о доступности.
- Дополнительные параметры и добавки, если они предусмотрены рестораном.

Пользователь может открыть карточку товара, ознакомиться с его характеристиками и добавить необходимое количество товара в корзину.

### Корзина


Корзина предназначена для формирования будущего заказа.

Пользователь должен иметь возможность:

- Добавлять товары в корзину.
- Удалять товары из корзины.
- Изменять количество выбранных товаров.
- Просматривать состав корзины.
- Видеть стоимость каждого товара.
- Видеть общую стоимость заказа.
- Выбирать время доставки.
- Проверять доступность товаров перед оформлением заказа.

При изменении количества товаров итоговая стоимость должна пересчитываться автоматически.

### Заказ


Заказ формируется на основе выбранных пользователем товаров из корзины.

При оформлении заказа пользователь указывает:

- состав заказа;
- количество каждого товара;
- адрес доставки;
- контактные данные;
- время доставки;
- способ оплаты.

После подтверждения заказ получает уникальный номер.

Система должна сохранять состав заказа, количество товаров и стоимость на момент его оформления.

Заказ проходит следующие состояния:

**Создан → Принят рестораном → Готовится → Передан курьеру → Доставляется → Доставлен.**

При необходимости заказ может быть отменён.

Пользователь должен иметь возможность:

- просматривать текущий статус заказа;
- просматривать состав заказа;
- просматривать стоимость;
- видеть выбранный адрес доставки;
- просматривать историю заказов;
- повторять ранее оформленный заказ.

### Оплата


- Выбор способа оплаты.
- Интеграция с платежными шлюзами (Stripe / YooKassa / SberPay).
- Проверка результата оплаты.
- Отображение пользователю информации об успешной или неуспешной оплате.

### Доставка


- Выбор адреса доставки.
- Выбор ближайшего или отложенного времени доставки.
- Передача заказа курьеру.
- Отображение текущего состояния доставки.
- Информирование пользователя об изменении статуса заказа.

### Личный кабинет


- Просмотр истории заказов.
- Повтор заказа (копирование состава корзины).
- Управление сохранёнными адресами.
- Редактирование личных данных.
- Просмотр информации о текущих заказах.

### Административная панель


- CRUD-операции для ресторанов и блюд.
- Добавление, изменение и удаление информации о товарах.
- Управление промокодами и акциями.
- Просмотр пользователей.
- Мониторинг текущих заказов в реальном времени.
- Управление статусами заказов.

### 4.2. Нефункциональные требования


- **Производительность:** API должно отвечать на 95% запросов за время < 300 мс (под нагрузкой до 5000 RPS).
- **Доступность:** время безотказной работы системы (SLA) — 99.9% (не более 8 часов простоя в год).
- **Надёжность:** система должна корректно обрабатывать ошибки и не допускать потери данных при стандартных сбоях.
- **Безопасность:**
  - Хранение паролей с использованием алгоритма bcrypt.
  - Использование HTTPS с валидными SSL-сертификатами.
  - Защита от основных угроз OWASP Top 10 (SQL-инъекции, XSS, CSRF).
- **Масштабируемость:** горизонтальное масштабирование микросервисов и базы данных с использованием репликации.
- **Кроссплатформенность:** поддержка последних версий Google Chrome, Mozilla Firefox, Safari, а также адаптивный дизайн для мобильных устройств.
- **Удобство использования:** основные действия пользователя должны выполняться без большого количества переходов между страницами.

### 4.3. Технический стек (Требования к технологиям)


#### Frontend


- **Язык:** TypeScript / JavaScript.
- **Фреймворк:** React.
- **Сборка проекта:** Vite.
- **Разметка:** HTML5.
- **Стилизация:** CSS3.
- **Взаимодействие с сервером:** REST API через HTTPS.
- **Адаптивность:** поддержка настольных компьютеров, планшетов и мобильных устройств.

#### Backend


- **Язык:** Python 3.10+.
- **Фреймворк:** FastAPI / Django REST Framework.
- **База данных:** PostgreSQL (основная), Redis (кеширование и брокер задач).
- **Очереди:** Celery / RabbitMQ для асинхронной обработки (уведомления, рассылки).
- **Сервер:** Gunicorn + Nginx.

#### Взаимодействие компонентов


Клиентская часть отправляет запросы к серверу через REST API. Сервер обрабатывает запросы, взаимодействует с базой данных и возвращает результат клиентскому приложению.

Основные операции:

**Frontend → REST API → Backend → PostgreSQL / Redis → Backend → Frontend**

## 5. Требования к документации


Документация по проекту является неотъемлемой частью поставки и должна обеспечивать полное понимание системы для разработчиков, тестировщиков, администраторов и конечных пользователей.

### 5.1. Состав документации


- **Техническое задание (ТЗ)** — утверждённый документ с требованиями заказчика.
- **Архитектурная документация** — описание структуры приложения, взаимодействия компонентов, схемы данных и диаграммы последовательности (в формате PlantUML или Draw.io).
- **API-документация** — спецификация всех REST/GraphQL эндпоинтов в формате OpenAPI (Swagger) с примерами запросов и ответов.
- **Документация по базам данных** — ER-диаграмма, описание таблиц, индексов и миграций (автоматически генерируется через Alembic).
- **Руководство разработчика** — инструкции по установке, сборке, запуску тестов, линтерам, а также описание структуры кода.
- **Руководство администратора** — описание развертывания в production, настройка мониторинга, резервное копирование, восстановление и обновление.
- **Руководство пользователя** — описание интерфейса, сценариев использования и решения типовых проблем (в формате PDF или интерактивной справки).
- **Тест-план и тест-кейсы** — документы для QA-команды, которые могут быть представлены в виде чек-листов.

### 5.2. Форматы и хранение


- Все текстовые документы хранятся в репозитории в формате **Markdown** (`.md`) для удобства версионирования.
- Схемы и диаграммы сохраняются в виде файлов `drawio` или `puml`, а их экспортированные версии (PNG/SVG) помещаются в папку `/docs/images`.
- API-документация генерируется автоматически из кода и доступна по эндпоинту `/api/docs` (Swagger UI) и `/api/redoc`.
- Версии документации синхронизируются с релизными тегами (каждому релизу соответствует своя версия docs).
- Актуальность контролируется при каждом Pull Request: изменение API требует обновления OpenAPI-спецификации.

## 7. Этапы разработки


Разработка ведётся по гибкой методологии **Scrum** с двухнедельными спринтами. Проект разделён на следующие укрупнённые этапы:

| **Этап** | **Название** | **Длительность** | **Основные результаты** |
|---|---|---|---|
| **0** | **Анализ и проектирование** | 3 недели | Согласованное ТЗ, архитектурное решение, утверждённые макеты UI/UX, спроектированная схема БД. |
| **1** | **Разработка базового ядра** | 4 спринта (8 недель) | Система аутентификации, каталог ресторанов и блюд, REST API для мобильных и веб-клиентов. |
| **2** | **Разработка функций заказа и оплаты** | 3 спринта (6 недель) | Корзина, оформление заказа, интеграция с платежным шлюзом, модуль уведомлений. |
| **3** | **Административная панель и личный кабинет** | 2 спринта (4 недели) | Панель управления для ресторанов и администраторов, история заказов пользователей, система промокодов. |
| **4** | **Интеграционное тестирование и нагрузочное тестирование** | 1 спринт (2 недели) | Проведение всех видов тестирования, исправление критических багов, оптимизация производительности. |
| **5** | **Пилотный запуск (Beta)** | 4 недели | Развертывание на ограниченной аудитории, сбор обратной связи, доработка функций. |
| **6** | **Релиз и внедрение** | 2 недели | Финальное развертывание, перенос данных, обучение администраторов, запуск рекламной кампании. |
| **7** | **Сопровождение и развитие** | Постоянно | Поддержка стабильности, выпуск обновлений, добавление новых функций согласно бэклогу. |

Детальные планы по каждому спринту ведутся в системе управления проектами (Jira / YouTrack).

## 8. Процесс контроля и приёмки


### 8.1. Организация контроля качества


- **Code Review** — каждый Pull Request проверяется минимум двумя разработчиками (используется GitHub Pull Requests с обязательными аппрувами).
- **Статический анализ** — автоматический запуск линтеров (ESLint, Pylint) и проверка форматирования (Prettier, Black) через pre-commit хуки.
- **Модульное тестирование** — покрытие кода тестами должно быть ≥80% (используется PyTest для бэкенда, Jest для фронтенда).
- **Интеграционное тестирование** — проверка взаимодействия компонентов и внешних систем (платежи, SMS-шлюзы) в отдельной среде staging.
- **Нагрузочное тестирование** — проводится перед каждым мажорным релизом с использованием Apache JMeter или Locust.
- **Тестирование безопасности** — сканирование зависимостей на уязвимости (Snyk, Dependabot) и регулярный пентест (раз в квартал).

### 8.2. Критерии приёмки релиза


- Все автоматические тесты (CI/CD пайплайн) проходят успешно.
- Критические и высокоприоритетные баги (Severity ≥ Major) исправлены или задокументированы с планом исправления.
- Документация обновлена и соответствует текущей версии кода.
- Получено согласование от владельца продукта (Product Owner) по результатам демонстрации.
- Проведено smoke-тестирование на production-подобном окружении.
- Выполнено бэкап-восстановление (проверка процедуры отката).

### 8.3. Процедура приёмочного тестирования (UAT)


1. Заказчик (или представитель) выполняет предопределённый набор тест-кейсов из утверждённого тест-плана.
2. Все расхождения фиксируются в баг-трекере (Jira).
3. После устранения критических замечаний заказчик подписывает акт приёмки выполненных работ.
4. Версия получает тег `release-x.y.z` в репозитории, и начинается развертывание на production.

### 8.4. Отслеживание дефектов


- Используется баг-трекер с классификацией по приоритетам (Blocker, Critical, Major, Minor, Trivial).
- Требуется время реакции: Blocker — в течение 4 часов, Critical — 24 часа, Major — 3 рабочих дня.

# Приложение для онлайн-заказа еды (Food Delivery App) Тарабанов и Новгородов

---

## 1. Введение

**Food Delivery App** — это полнофункциональная платформа, объединяющая пользователей (клиентов), рестораны и службу доставки в единой экосистеме. 

Приложение позволяет:
- Просматривать каталог ресторанов и блюд.
- Фильтровать предложения по кухне, рейтингу, времени доставки.
- Оформлять заказы с выбором способа оплаты.
- Отслеживать статус заказа в реальном времени.
- Управлять личным кабинетом и историей покупок.

Проект реализован как SPA (Single Page Application) с использованием микросервисной архитектуры на бэкенде для обеспечения отказоустойчивости и независимости развертывания компонентов.

---

## 2. Основания для разработки

Разработка данного приложения инициирована на основе следующих факторов:

- **Анализ рынка:** Высокий спрос на сервисы доставки готовой еды в городской среде (рост рынка на 25% в 2023–2024 гг.).
- **Бизнес-задача:** Создание конкурентного решения, которое объединяет функцию агрегатора с собственной логистикой, снижая комиссию для ресторанов по сравнению с текущими гигантами рынка.
- **Техническая необходимость:** Устаревшие решения конкурентов не предоставляют гибких API для интеграции с системами лояльности и корпоративными заказами.
- **Внутренние потребности:** Стандартизация процессов приема заказов для ресторанов-партнеров и автоматизация работы курьерской службы.

---

## 3. Назначение продукта

### Целевая аудитория
1. **Конечные пользователи:** Физические лица, желающие заказать еду с доставкой на дом или в офис.
2. **Рестораны и кафе:** Заведения общественного питания, подключающиеся к платформе для приема заказов.
3. **Администраторы платформы:** Менеджеры, управляющие акциями, модерацией контента и обработкой спорных транзакций.
4. **Курьеры:** Исполнители доставки, получающие заказы через мобильное приложение курьера.

### Основные бизнес-цели
- **Увеличение продаж:** Обеспечение ресторанов дополнительным каналом сбыта.
- **Удобство пользователей:** Интуитивно понятный интерфейс с минимальным количеством шагов для оформления заказа (от 3 до 5 кликов).
- **Автоматизация:** Полная автоматизация процессов от принятия заказа до передачи его в кухонную систему ресторана (KDS).
- **Аналитика:** Сбор данных о предпочтениях пользователей для построения персонализированных рекомендаций.

## 4. Требования к ПО

Данный раздел описывает функциональные, нефункциональные и технологические требования, предъявляемые к разрабатываемой системе.

### 4.1. Функциональные требования

- **Модуль аутентификации:**
  - Регистрация/Вход по email/паролю или через соцсети (Google, Apple).
  - Восстановление пароля с подтверждением по SMS/Email.
- **Каталог:**
  - Поиск по названию блюда и ингредиентам.
  - Фильтрация: по цене, рейтингу, типу кухни, времени доставки.
  - Подгрузка изображений блюд через CDN.
- **Корзина и заказ:**
  - Добавление/удаление позиций, изменение количества.
  - Выбор времени доставки (ближайшее или отложенное).
  - Интеграция с платежными шлюзами (Stripe / YooKassa / SberPay).
- **Личный кабинет:**
  - Просмотр истории заказов.
  - Повтор заказа (копирование состава корзины).
  - Управление сохраненными адресами.
- **Административная панель:**
  - CRUD операции для ресторанов и блюд.
  - Управление промокодами и акциями.
  - Мониторинг текущих заказов в реальном времени.

### 4.2. Нефункциональные требования

- **Производительность:** API должно отвечать на 95% запросов за время < 300 мс (под нагрузкой до 5000 RPS).
- **Доступность:** Время безотказной работы системы (SLA) — 99.9% (не более 8 часов простоя в год).
- **Безопасность:** 
  - Хранение паролей с использованием алгоритма bcrypt.
  - Использование HTTPS с валидными SSL-сертификатами.
  - Защита от основных угроз OWASP Top 10 (SQL инъекции, XSS, CSRF).
- **Масштабируемость:** Горизонтальное масштабирование микросервисов и базы данных с использованием репликации.
- **Кроссплатформенность:** Поддержка последних версий Google Chrome, Mozilla Firefox, Safari, а также адаптивный дизайн для мобильных устройств.

### 4.4. Требования к окружению разработки
- Установленный **Git**.
- **Docker** и **Docker Compose** (для запуска зависимостей локально).
- **Make** (для автоматизации команд сборки).
- Переменные окружения (`.env` файл) с конфигурацией для подключения к БД и внешним API.

### 4.3. Технический стек (Требования к технологиям)

#### Backend
- **Язык:** Python 3.10+ 
- **Фреймворк:** FastAPI / Django REST Framework.
- **База данных:** PostgreSQL (основная), Redis (кеширование и брокер задач).
- **Очереди:** Celery / RabbitMQ для асинхронной обработки (уведомления, рассылки).
- **Сервер:** Gunicorn + Nginx.

## 5. Требования к документации

Документация по проекту является неотъемлемой частью поставки и должна обеспечивать полное понимание системы для всех категорий участников (разработчики, тестировщики, администраторы, конечные пользователи).

### 5.1. Состав документации
- **Техническое задание (ТЗ)** – утверждённый документ с требованиями заказчика.
- **Архитектурная документация** – описание микросервисной структуры, взаимодействия компонентов, схема данных, диаграммы последовательности (в формате PlantUML или Draw.io).
- **API-документация** – спецификация всех REST/GraphQL эндпоинтов в формате OpenAPI (Swagger) с примерами запросов/ответов.
- **Документация по базам данных** – ER-диаграмма, описание таблиц, индексов, миграций (автоматически генерируется через Alembic).
- **Руководство разработчика** – инструкции по установке, сборке, запуску тестов, линтерам, а также описание структуры кода.
- **Руководство администратора** – описание развертывания в production, настройка мониторинга, резервное копирование, восстановление, обновление.
- **Руководство пользователя** – описание интерфейса, сценариев использования, решения типовых проблем (в формате PDF или интерактивной справки).
- **Тест-план и тест-кейсы** – документы для QA-команды (могут быть в виде чек-листов в TestRail или аналогичных системах).

### 5.2. Форматы и хранение
- Все текстовые документы хранятся в репозитории в формате **Markdown** (`.md`) для удобства версионирования.
- Схемы и диаграммы сохраняются в виде файлов `drawio` или `puml`, а их экспортированные версии (PNG/SVG) помещаются в папку `/docs/images`.
- API-документация генерируется автоматически из кода и доступна по эндпоинту `/api/docs` (Swagger UI) и `/api/redoc`.
- Версии документации синхронизируются с релизными тегами (каждому релизу соответствует своя версия docs).
- Актуальность контролируется при каждом Pull Request: изменение API требует обновления OpenAPI-спецификации.

## 7. Этапы разработки

Разработка ведётся по гибкой методологии **Scrum** с двухнедельными спринтами. Проект разделён на следующие укрупнённые этапы:

| Этап | Название | Длительность | Основные результаты |
|------|----------|--------------|----------------------|
| **0** | **Анализ и проектирование** | 3 недели | Согласованное ТЗ, архитектурное решение, утверждённые макеты UI/UX, спроектированная схема БД. |
| **1** | **Разработка базового ядра** | 4 спринта (8 недель) | Система аутентификации, каталог ресторанов и блюд, REST API для мобильных и веб-клиентов. |
| **2** | **Разработка функций заказа и оплаты** | 3 спринта (6 недель) | Корзина, оформление заказа, интеграция с платежным шлюзом, модуль уведомлений. |
| **3** | **Административная панель и личный кабинет** | 2 спринта (4 недели) | Панель управления для ресторанов и администраторов, история заказов пользователей, система промокодов. |
| **4** | **Интеграционное тестирование и нагрузочное тестирование** | 1 спринт (2 недели) | Проведение всех видов тестирования, исправление критических багов, оптимизация производительности. |
| **5** | **Пилотный запуск (Beta)** | 4 недели | Развертывание на ограниченной аудитории, сбор обратной связи, доработка функций. |
| **6** | **Релиз и внедрение** | 2 недели | Финальное развертывание, перенос данных, обучение администраторов, запуск рекламной кампании. |
| **7** | **Сопровождение и развитие** | Постоянно | Поддержка стабильности, выпуск обновлений, добавление новых фич согласно бэклогу. |

Детальные планы по каждому спринту ведутся в системе управления проектами (Jira / YouTrack).

## 8. Процесс контроля и приёмки

### 8.1. Организация контроля качества
- **Code Review** – каждый Pull Request проверяется минимум двумя разработчиками (используется GitHub Pull Requests с обязательными аппрувами).
- **Статический анализ** – автоматический запуск линтеров (ESLint, Pylint) и проверка форматирования (Prettier, Black) через pre-commit хуки.
- **Модульное тестирование** – покрытие кода тестами должно быть ≥80% (используется PyTest для бэкенда, Jest для фронтенда).
- **Интеграционное тестирование** – проверка взаимодействия микросервисов и внешних систем (платежи, SMS-шлюзы) в отдельной среде staging.
- **Нагрузочное тестирование** – проводится перед каждым мажорным релизом с использованием Apache JMeter или Locust.
- **Тестирование безопасности** – сканирование зависимостей на уязвимости (Snyk, Dependabot) и регулярный пентест (раз в квартал).

### 8.2. Критерии приёмки релиза
- Все автоматические тесты (CI/CD пайплайн) проходят успешно.
- Критические и высокоприоритетные баги (Severity ≥ Major) исправлены или задокументированы с планом исправления.
- Документация обновлена и соответствует текущей версии кода.
- Получено согласование от владельца продукта (Product Owner) по результатам демонстрации.
- Проведено smoke-тестирование на production-подобном окружении.
- Выполнено бэкап-восстановление (проверка процедуры отката).

### 8.3. Процедура приёмочного тестирования (UAT)
1. Заказчик (или представитель) выполняет предопределённый набор тест-кейсов из утверждённого тест-плана.
2. Все расхождения фиксируются в баг-трекере (Jira).
3. После устранения критических замечаний заказчик подписывает акт приёмки выполненных работ.
4. Версия получает тег `release-x.y.z` в репозитории, и начинается развертывание на production.

### 8.4. Отслеживание дефектов
- Используется баг-трекер с классификацией по приоритетам (Blocker, Critical, Major, Minor, Trivial).
- Требуется время реакции: Blocker – в течение 4 часов, Critical – 24 часа, Major – 3 рабочих дня.

Приложение для онлайн-заказа еды (Food Delivery App) Тарабанов и Новгородов
svg
---
1. Введение
svg
Food Delivery App — это полнофункциональная платформа, объединяющая пользователей (клиентов), рестораны и службу доставки в единой экосистеме.
Приложение позволяет:
Просматривать каталог ресторанов, категорий и отдельных товаров.
Открывать карточку товара с его описанием, стоимостью, изображением и доступностью.
Фильтровать предложения по кухне, рейтингу, стоимости и времени доставки.
Добавлять товары в корзину, изменять их количество и удалять ненужные позиции.
Оформлять заказ с указанием адреса, способа получения и способа оплаты.
Отслеживать статус заказа в реальном времени.
Просматривать историю ранее оформленных заказов и повторять их.
Управлять личными данными и сохранёнными адресами.
Основной пользовательский сценарий выглядит следующим образом: пользователь выбирает ресторан, просматривает доступные товары, добавляет необходимые позиции в корзину, проверяет состав и итоговую стоимость, указывает адрес доставки и способ оплаты, после чего подтверждает заказ. Система передаёт информацию ресторану и службе доставки, а пользователь получает возможность отслеживать изменение статуса заказа.
Проект реализуется как SPA (Single Page Application). Клиентская часть отвечает за отображение интерфейса и взаимодействие с пользователем, а серверная часть обрабатывает бизнес-логику, работу с данными и обмен информацией между отдельными компонентами системы.

2. Основания для разработки
svg
Разработка данного приложения инициирована на основе следующих факторов:
Анализ рынка: Высокий спрос на сервисы доставки готовой еды в городской среде (рост рынка на 25% в 2023–2024 гг.).
Бизнес-задача: Создание конкурентного решения, которое объединяет функцию агрегатора с собственной логистикой, снижая комиссию для ресторанов по сравнению с текущими гигантами рынка.
Техническая необходимость: Устаревшие решения конкурентов не предоставляют гибких API для интеграции с системами лояльности и корпоративными заказами.
Внутренние потребности: Стандартизация процессов приема заказов для ресторанов-партнеров и автоматизация работы курьерской службы.

3. Назначение продукта
svg
Целевая аудитория
svg
Конечные пользователи: Физические лица, желающие заказать еду с доставкой на дом или в офис.
Рестораны и кафе: Заведения общественного питания, подключающиеся к платформе для приема заказов.
Администраторы платформы: Менеджеры, управляющие акциями, модерацией контента и обработкой спорных транзакций.
Курьеры: Исполнители доставки, получающие заказы через мобильное приложение курьера.
Основные бизнес-цели
svg
Увеличение продаж: Обеспечение ресторанов дополнительным каналом сбыта.
Удобство пользователей: Интуитивно понятный интерфейс с минимальным количеством шагов для оформления заказа (от 3 до 5 кликов).
Автоматизация: Полная автоматизация процессов от принятия заказа до передачи его в кухонную систему ресторана (KDS).
Аналитика: Сбор данных о предпочтениях пользователей для построения персонализированных рекомендаций.

Формирование заказа на основе содержимого корзины.

Указание адреса доставки и контактных данных пользователя.
Выбор ближайшего или отложенного времени доставки.

После оформления заказу присваивается уникальный номер.

Пользователь может просматривать состав заказа, его стоимость и текущий статус.
При необходимости заказ может быть отменён в соответствии с установленными правилами.
Оплата:
Выбор доступного способа оплаты при оформлении заказа.

Повтор ранее оформленного заказа.
Управление сохранёнными адресами.
Административная панель:
Добавление, изменение и удаление ресторанов и товаров.
Управление категориями и информацией о меню.
Управление промокодами и акциями.
Просмотр и контроль текущих заказов.
Управление учётными записями пользователей и ролями.

Использование HTTPS с валидными SSL-сертификатами.
Защита от основных угроз OWASP Top 10 (SQL инъекции, XSS, CSRF).
Масштабируемость: Горизонтальное масштабирование микросервисов и базы данных с использованием репликации.
Кроссплатформенность: Поддержка последних версий Google Chrome, Mozilla Firefox, Safari, а также адаптивный дизайн для мобильных устройств.
4.3. Технический стек (Требования к технологиям)
svg
Frontend
Язык: TypeScript / JavaScript.
Фреймворк: React.
Сборщик: Vite.
Интерфейс: HTML5 и CSS3 с адаптивной версткой.
Взаимодействие: REST API по протоколу HTTPS.
Frontend отвечает за отображение каталога, корзины, формы оформления заказа, личного кабинета и административного интерфейса. Обмен данными с серверной частью выполняется через API.
Backend
svg
Язык: Python 3.10+.
Фреймворк: FastAPI / Django REST Framework.
База данных: PostgreSQL.
Кэширование: Redis.
Очереди задач: Celery / RabbitMQ для асинхронных операций.
Сервер: Gunicorn + Nginx.
Backend реализует бизнес-логику приложения: работу пользователей, ресторанов, товаров, корзин и заказов, обработку оплаты, изменение статусов и взаимодействие с базой данных.
Взаимодействие компонентов
Клиентская часть обращается к backend через REST API. Backend принимает запрос, проверяет права доступа и корректность данных, выполняет необходимую операцию и возвращает результат клиенту. Данные о пользователях, товарах и заказах хранятся в PostgreSQL, а Redis используется для временных данных и ускорения отдельных операций.

svg
Документация по проекту является неотъемлемой частью поставки и должна обеспечивать полное понимание системы для всех категорий участников (разработчики, тестировщики, администраторы, конечные пользователи).
5.1. Состав документации
svg
Техническое задание (ТЗ) – утверждённый документ с требованиями заказчика.
Архитектурная документация – описание микросервисной структуры, взаимодействия компонентов, схема данных, диаграммы последовательности (в формате PlantUML или Draw.io).
API-документация – спецификация всех REST/GraphQL эндпоинтов в формате OpenAPI (Swagger) с примерами запросов/ответов.
Документация по базам данных – ER-диаграмма, описание таблиц, индексов, миграций (автоматически генерируется через Alembic).
Руководство разработчика – инструкции по установке, сборке, запуску тестов, линтерам, а также описание структуры кода.
Руководство администратора – описание развертывания в production, настройка мониторинга, резервное копирование, восстановление, обновление.
Руководство пользователя – описание интерфейса, сценариев использования, решения типовых проблем (в формате PDF или интерактивной справки).
Тест-план и тест-кейсы – документы для QA-команды (могут быть в виде чек-листов в TestRail или аналогичных системах).
5.2. Форматы и хранение
svg
Все текстовые документы хранятся в репозитории в формате Markdown (`.md`) для удобства версионирования.
Схемы и диаграммы сохраняются в виде файлов `drawio` или `puml`, а их экспортированные версии (PNG/SVG) помещаются в папку `/docs/images`.
API-документация генерируется автоматически из кода и доступна по эндпоинту `/api/docs` (Swagger UI) и `/api/redoc`.
Версии документации синхронизируются с релизными тегами (каждому релизу соответствует своя версия docs).
Актуальность контролируется при каждом Pull Request: изменение API требует обновления OpenAPI-спецификации.

8. Процесс контроля и приёмки
svg
8.1. Организация контроля качества
svg
Code Review – каждый Pull Request проверяется минимум двумя разработчиками (используется GitHub Pull Requests с обязательными аппрувами).
Статический анализ – автоматический запуск линтеров (ESLint, Pylint) и проверка форматирования (Prettier, Black) через pre-commit хуки.
Модульное тестирование – покрытие кода тестами должно быть ≥80% (используется PyTest для бэкенда, Jest для фронтенда).
Интеграционное тестирование – проверка взаимодействия микросервисов и внешних систем (платежи, SMS-шлюзы) в отдельной среде staging.
Нагрузочное тестирование – проводится перед каждым мажорным релизом с использованием Apache JMeter или Locust.
Тестирование безопасности – сканирование зависимостей на уязвимости (Snyk, Dependabot) и регулярный пентест (раз в квартал).
8.2. Критерии приёмки релиза
svg
Все обязательные автоматические тесты проходят успешно.
Основные пользовательские сценарии выполняются без критических ошибок.
Критические дефекты исправлены до выпуска релиза.
Функции регистрации, каталога, товара, корзины, оформления и отслеживания заказа работают в соответствии с требованиями.
Документация обновлена и соответствует текущей версии приложения.
Выполнено smoke-тестирование основных функций.
Получено подтверждение готовности версии к выпуску.
8.3. Процедура приёмочного тестирования (UAT)
svg
Заказчик (или представитель) выполняет предопределённый набор тест-кейсов из утверждённого тест-плана.
Все расхождения фиксируются в баг-трекере (Jira).
После устранения критических замечаний заказчик подписывает акт приёмки выполненных работ.
Версия получает тег `release-x.y.z` в репозитории, и начинается развертывание на production.
8.4. Отслеживание дефектов
svg
Используется баг-трекер с классификацией по приоритетам (Blocker, Critical, Major, Minor, Trivial).
Требуется время реакции: Blocker – в течение 4 часов, Critical – 24 часа, Major – 3 рабочих дня.

В данном разделе перечислены вспомогательные артефакты и ссылки, которые дополняют основное описание проекта и поставляются вместе с ним.
№НаименованиеОписаниеМестонахождение			
1	Макеты пользовательского интерфейса	Файлы Figma с дизайном всех экранов (клиентская часть, админка, приложение курьера).	Ссылка на Figma
2	Схема базы данных (ER-диаграмма)	Детальная модель данных с указанием всех таблиц, полей, связей и индексов.	`/docs/er\\\_diagram.puml` и `/docs/images/er\\\_diagram.png`
3	Спецификация API (OpenAPI)	Файл `openapi.yaml`, сгенерированный автоматически из кода (доступен также в Swagger UI).	`/api/openapi.yaml` (эндпоинт `/api/docs`)
4	Архитектурные диаграммы	Схемы развертывания, взаимодействия микросервисов, потоков данных (C4-модель).	`/docs/architecture/`
5	Перечень внешних зависимостей	Список всех используемых библиотек, фреймворков и сервисов с версиями и лицензиями.	`/backend/requirements.txt`, `/frontend/package.json`
6	Инструкция по развертыванию	Подробное руководство по установке на сервер (включая настройку HTTPS, балансировщиков, мониторинга).	`/docs/deployment.md`
7	План тестирования	Описание стратегии тестирования, объёма тестов, используемых инструментов и окружений.	`/docs/test\\\_plan.md`
8	Журнал изменений (CHANGELOG)	Хронологический список всех изменений по версиям с группировкой (Added, Changed, Fixed, Removed).	`/CHANGELOG.md`
9	Лицензионные соглашения	Копии лицензий на используемое ПО с открытым исходным кодом (если применимо).	`/licenses/`
10	Результаты нагрузочного тестирования	Отчёты JMeter/Locust с графиками производительности для различных сценариев.	`/docs/performance\\\_reports/`
Все перечисленные приложения доступны в репозитории или по прямым ссылкам. Актуальность приложений поддерживается в рамках каждого
